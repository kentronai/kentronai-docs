A skill is a set of instructions your organization writes once — how to triage an incident, how to format a competitive analysis, which account to check first — so that every background run can follow them instead of being told again in each conversation. You upload one `SKILL.md` file per skill, enable the ones you want in use, and every new run receives them as a read-only catalog the agent can draw on.

The Skills page is where they are managed: upload, enable, disable, view and delete, with a receipt behind every change. Picking a skill inside a conversation is covered in [using skills in chat](/co-worker/skills-in-chat); the file format itself is in [writing a skill](/catalog/writing-a-skill).

## Opening the Skills page

Skills are at `/organization/settings/skills`, reachable from the **Skills** icon in the organization settings rail. Three shortcuts lead to the same page:

| Where | What it opens |
|---|---|
| The chat composer's **Skills** chip | **Create skill** opens the page with its upload picker already up; **Manage skills** opens the list |
| The chat composer's `+` menu → **Skills** | **Create skill**, which opens the page without the picker |
| Cmd/Ctrl+K → **Skills** | The page, from the command palette |

Like the rest of organization settings, the page is owner and admin only. A member who follows any of these shortcuts is sent back to the app root — there is no access-denied screen — and the server enforces the same rule independently, refusing a write from anyone else with **"Only organization owners or admins can manage skills."** Using a skill is not restricted this way: the composer's picker offers enabled skills to every member.

The page describes itself as:

> Add organization instructions that agents can use in Factory and computer runs. Enabled skills are available to new runs.

The primary action is **Add skill**, which becomes **Adding skill** with a spinner while the upload is in flight. A **Search skills** box filters the list by name, slug, description or version, and the count line reads `Showing {n} of {m} matching skills ({total} total)`, or "Loading skills" while it resolves. With no match: **"No skills found. Try a different search."** The table shows 25 rows a page, and the pager under it also offers 10, 50 and 100.

Before you upload anything the empty state reads **"No organization skills yet"** — "Upload a SKILL.md bundle to make reusable instructions available to new agent and computer runs." — with an **Add your first skill** button.

## What you can upload

The upload is a single file, and the contract is strict.

| Requirement | If you break it |
|---|---|
| The file must be named `SKILL.md` (case-insensitive) | `Choose a file named SKILL.md.` |
| The file must not be empty | `The skill file is empty.` |
| The file must be 256 KB or smaller | `Skill files must be 256 KB or smaller.` |

The file picker accepts `.md`, `.markdown` and `text/markdown`. These three checks run in the browser, and a rejection appears in an error banner above the table rather than as a passing toast; a failure raised by the server appears in the same banner and as a toast. What has to be inside the file — the `---` frontmatter block, `name` and `description`, and the parser's exact complaints — is on [writing a skill](/catalog/writing-a-skill).

<Info>
The underlying bundle format supports up to 128 files, with a path limit of 240 bytes and a total of 1 MiB. The upload surface in the application accepts exactly one file — the `SKILL.md` itself.
</Info>

## Versions, not replacements

Uploading the same slug again **adds a new version**: the version number advances, runs receive the newest version, and the earlier one stays on the skill's receipt stream. The file input clears after each upload so you can re-upload the same file as a replacement version immediately. Re-uploading a file whose content has not changed at all is a no-op: no version is added, and the page reports nothing.

Versions are recorded as receipt events — `organization.skill.created` for version 1, then `.version_added` for every version from 2 upward, alongside `.save_acknowledged`, `.enabled_changed`, `.archived` and `.deleted`. A skill's identity is its slug, derived from its name, so two admins uploading the same name land on one skill rather than forking into two.

## The table and the detail view

Columns are **# / Skill / Status / Version / Bundle / Updated / Actions**. The skill cell shows the name, the `/slug` in monospace, and the description. Status is one of the badges **Archived**, **Enabled** or **Disabled**. Version renders as `v{n}`; Bundle shows the file count and the size in B, KB or MB.

Opening a skill shows a read-only detail dialog — "Read-only organization skill instructions from the authoritative receipt-backed bundle." — exposing **Slug**, **Version** and **Content hash**, with a file picker when the bundle holds more than one file and a **Copy file** button that flips to **Copied**. A binary file renders as `Binary file · base64 encoded · {size}` rather than content. If the copy fails, you get "Unable to copy this file. Select the text and copy it manually."

Skill metadata is replicated to owner and admin browsers; bundle contents stay on the server and are fetched only when you open the detail dialog. Separately, the name, slug and description of enabled skills reach every member's browser, because that is what the composer's picker shows.

## Row actions

  <img src="/images/catalog/skills-row-actions.png" alt="The Skills table with a row menu open showing three items: View details, Disable, and Delete." />

**View details** opens the read-only dialog above. **Disable** takes the skill out of new runs and out of the composer's picker without deleting anything, and reads **Enable** on a disabled row. **Delete** asks for confirmation.

<Note>
There is no **Archive** action in the table. Archived is a status a row can carry — an archived row shows the **Archived** badge, offers no enable or disable toggle, and can only be deleted — but nothing in the interface puts a skill into that state.
</Note>

The delete dialog is titled **"Delete skill?"** and reads `Delete {name}? It will be removed from this list and will no longer be available to new agent or computer runs.`, with the help line "Existing receipts keep their version and content hash for audit, and the skill name becomes available again."

So deletion is forward-looking: new runs stop receiving the skill, every receipt already written keeps the exact version and content hash it ran with, and the name becomes free to use again.

## Where an enabled skill goes in a run

Enabled skills are snapshotted when the work packet for a task is written, which is what the page means by "Enabled skills are available to new runs" — enabling or disabling a skill reaches the packets written after the change, not a task already executing.

At that moment every enabled skill is written into the task's workspace under **`receipt/skills/organization/<slug>/`**, with a catalog at **`receipt/skills/index.json`** listing each skill's name, description, version, content hash and the path to its `SKILL.md`. The registry that writes it enforces its own guards: **256 files per skill**, **4 MiB per file** and **8 MiB per skill**. The tree is then locked read-only — files and the index readable but not writable, directories not writable — and the agent is given no way to refresh it. Nothing a worker changes there can come back as a patch: those paths are excluded from patch collection and rejected outright if they appear anyway.

Organization skills stay in this workspace catalog and are never copied into the agent's home directory. The packet's summary tells the agent only that every enabled skill is mounted and cataloged at `receipt/skills/index.json`, and that it chooses which entries to load. One of the skills that ships with Receipt states the rule for reading that catalog:

> 1. Read `receipt/skills/index.json`. It is the complete compact catalog for the run, including each skill's name, description, version, content hash, and guest-workspace-relative `skillPath`.
> 2. Select the smallest relevant set using the task, plan, and catalog metadata. Do not read every `SKILL.md` merely because it is mounted.
> 3. Read each selected `skillPath` completely before acting on it. Resolve any relative references from that skill's directory.

<Warning>
**Receipt does not choose skills for the agent, and no receipt records which skill was read.** There is no ranking, keyword matching or auto-selection: the whole enabled catalog is mounted and the agent decides what to open. Receipts and the run's packet establish which skills were *available* — the catalog's hash is folded into the packet — not which of them were actually used.
</Warning>

Enabling a skill therefore puts it in front of every new run; it does not compel the run to follow it, and it never widens what the run may do. Write access is still decided per connection, in [tools and permissions](/mcp-gateway/tools-and-permissions).

## Skills that ship with Receipt

Alongside your organization's skills, Receipt carries its own checked-in skills, written by the engineers who build it: how a worker should behave, how to reach connected systems through the CLI, how to publish a pull request. A selected subset is copied into the run's isolated agent home, chosen from the run's profile and the kind of work — cloud-specific ones appear only when the run has a cloud execution context. Your organization's skills stay in the read-only catalog above instead. Beside them sits a helper catalog: runnable scripts with a fixed result contract that those skills tell the agent to prefer over ad-hoc shell commands. Neither is uploaded or configured from the application, and neither replaces an organization skill — they are instructions for operating Receipt, not for your business.
