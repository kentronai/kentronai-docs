---
title: "Organization skills and knowledge"
description: "Two organization-wide surfaces: reusable SKILL.md instructions that agents pick up in a run, and Markdown or PDF documents that chat can retrieve from."
---

Receipt has two separate places to put material an organization shares with every run. **Skills** are instructions; **Knowledge** is documents. They have different upload contracts, different failure modes and different consumers, and neither is the other.

Both are owner and admin only, like the rest of organization settings.

## Skills

Skills are at `/organization/settings/skills`, reachable from the **Skills** icon in the organization settings rail. The page describes itself as:

> Add organization instructions that agents can use in Factory and computer runs. Enabled skills are available to new runs.

The primary action is **Add skill**, which becomes **Adding skill** with a spinner while the upload is in flight. A **Search skills** box filters the list, and the count line reads `Showing {n} of {m} matching skills ({total} total)`, or "Loading skills" while it resolves. With no match: **"No skills found. Try a different search."**

Before you upload anything the empty state reads **"No organization skills yet"** — "Upload a SKILL.md bundle to make reusable instructions available to new agent and computer runs." — with an **Add your first skill** button.

### What you can upload

The upload is a single file, and the contract is strict.

| Requirement | If you break it |
|---|---|
| The file must be named `SKILL.md` (case-insensitive) | `Choose a file named SKILL.md.` |
| The file must not be empty | `The skill file is empty.` |
| The file must be 256 KB or smaller | `Skill files must be 256 KB or smaller.` |

The file picker accepts `.md`, `.markdown` and `text/markdown`.

### The frontmatter contract

`SKILL.md` must open with a `---` line, close it with another `---`, and provide `name` and `description` inside. Folded (`>`) and literal (`|`) blocks are supported for the description.

The parser is deliberately minimal — it is not a general-purpose YAML parser, so keep the frontmatter to what the contract asks for. Its failures are:

| Message | Cause |
|---|---|
| `SKILL.md must start with YAML frontmatter.` | The file does not begin with `---` |
| `SKILL.md frontmatter is not closed.` | No closing `---` |
| `Skill name exceeds 120 characters.` | `name` is too long |
| `Skill description exceeds 2000 characters.` | `description` is too long |

<Info>
The underlying bundle format supports up to 128 files, with a path limit of 240 bytes and a total of 1 MiB. The upload surface in the application accepts exactly one file — the `SKILL.md` itself.
</Info>

### Versions, not replacements

Uploading the same slug again **adds a new version**; it does not overwrite the old one. The file input clears after each upload so you can re-upload the same file as a replacement version immediately.

Versions are recorded as receipt events — `organization.skill.created` for version 1, then `.version_added` for every version from 2 upward, alongside `.save_acknowledged`, `.enabled_changed`, `.archived` and `.deleted`.

### The table and the detail view

Columns are **# / Skill / Status / Version / Bundle / Updated / Actions**. The skill cell shows the name, the `/slug` in monospace, and the description. Status is one of the badges **Archived**, **Enabled** or **Disabled**. Version renders as `v{n}`; bundle size in B, KB or MB.

Opening a skill shows a read-only detail dialog — "Read-only organization skill instructions from the authoritative receipt-backed bundle." — exposing **Slug**, **Version** and **Content hash**, with a file picker when the bundle holds more than one file and a **Copy file** button that flips to **Copied**. A binary file renders as `Binary file · base64 encoded · {size}` rather than content. If the copy fails, you get "Unable to copy this file. Select the text and copy it manually."

Skill metadata is replicated to admin browsers; bundle contents stay on the server and are fetched only when you open the detail dialog.

### Where an enabled skill goes in a run

An enabled skill is mounted into a Factory run's guest workspace at **`receipt/skills/organization/`**, with an index at **`receipt/skills/index.json`**. The registry that writes it enforces its own guards: **256 files per skill**, **4 MiB per file** and **8 MiB per skill**. Files are written with restrictive permissions — `0600` for files, `0700` for directories.

Skills sit outside the agent's home directory on purpose, so the agent can discover them through the index without every skill's instructions being activated eagerly.

### Deleting a skill

The delete dialog is titled **"Delete skill?"** and reads `Delete {name}? It will be removed from this list and will no longer be available to new agent or computer runs.`, with the help line "Existing receipts keep their version and content hash for audit, and the skill name becomes available again."

So deletion is forward-looking: new runs stop receiving the skill, and every receipt already written keeps the exact version and content hash it ran with.

<Note>
Skills can also be saved from app chat rather than uploaded here. That path re-checks your membership against the authoritative table rather than trusting the request, and refuses with **"Only organization owners or admins can save organization skills. No skill changed."**
</Note>

## Knowledge

Organization knowledge is at `/organization/settings/knowledge`. It has **no rail icon and no menu entry** — it is reachable only by typing the URL.

The page is headed **"Organization Knowledge"**, described as "Upload Markdown or PDF files for your organization's knowledge base." This is organization-wide retrieval over documents you upload, and it is a different surface from **Org Brain** at `/organization/settings/knowledge-graph`, which is a read-only analytics dashboard over run activity, not a document store.

### What you can upload

Knowledge accepts `.pdf`, `.md` and `.markdown`, up to **25 MB** per file.

<Info>
That 25 MB ceiling applies only here. A file attached to a chat message is limited to **10 MB** — a different limit for a different surface.
</Info>

The upload button is labelled **Upload file**. Before anything is uploaded the page reads "No organization knowledge files have been uploaded yet."; while loading, "Loading organization knowledge...". A **Filter knowledge files...** input narrows the list.

### Status and indexing

The table columns are **File / Status / Last indexed**, plus a row actions menu.

Each file carries two independent states. Its activation state is **Active** or **Inactive**. Its index state is **Indexed**, **Pending index**, **Index error**, or **"Not indexed yet"** if it has never been indexed.

The row menu offers **Activate** or **Deactivate**, **Retry index**, and **Delete**.

When indexing fails you get a summarised reason rather than the underlying error, because raw errors can carry internal paths and backend details:

| Message |
|---|
| `Vector indexing timed out` |
| `Vector store request failed` |
| `Vector indexing is not configured` |
| `File conversion failed during indexing` |
| `Vector indexing failed` |

### How retrieval is switched on

There is no toggle for organization knowledge anywhere in the application. **Activating at least one file flips the organization's knowledge flag to true**, and that flag is what gates retrieval into chat prompts. Deactivating everything drops the active count back to zero and the flag with it.

Organization knowledge also depends on the embedding stack being available in the deployment: embedding must be enabled (`VITE_ENABLE_EMBEDDING`) and a vector store must be configured and reachable. Without it, indexing reports `Vector indexing is not configured`.
