title: "The MCP gateway"
description: "Point an MCP client at Receipt, and understand which tools the aggregate gateway publishes and which it deliberately holds back."
---

Receipt exposes **one** aggregate MCP server, at `POST /connect/mcp`. Every connection in the workspace your token is bound to is flattened into that single tool namespace, so a client connects once rather than once per provider.

## The server

| Property | Value |
| --- | --- |
| Endpoint | `POST /connect/mcp` |
| Server identity | `{ "name": "receipt-connect", "version": "1.0.0" }` |
| Capabilities | `{ "tools": { "listChanged": false } }` |
| Protocol versions | `2025-11-25` and `2025-06-18` |
| Methods | `initialize`, `notifications/initialized`, `tools/list`, `tools/call` |

The endpoint requires a token carrying `connect:credential`, and membership of the workspace that token is bound to. An unknown requested protocol version falls back to the first supported version rather than failing the handshake. `notifications/initialized` answers 202 with no body. `tools/list` rejects a `cursor` parameter. Any other method returns JSON-RPC `-32601 Method not found`.

## The instructions the server sends

The server ships an `instructions` string to every client that connects. It is not decoration — it states the rules a client has to obey, verbatim:

> Receipt tools are reviewed operations scoped to the organization and workspace authenticated by the saved CLI session. Tool names from tools/list are opaque; use them exactly and never construct aliases. Read-only annotations are authoritative. Writes appear only when the token and connection policy allow them; do not bypass a missing tool. read-provider-resource is GET-only and accepts only a provider-relative path and query. Re-list tools after switching workspaces or reconnecting.

## Tool names are opaque aliases

Published names take the form:

```text
receipt_<provider>_<connection>_<tool>_<20 hex characters>
```

The hex suffix is a digest over the connection id, the provider, the connection name and the upstream tool name. The readable prefix in front of it is trimmed as needed so the whole name stays at 128 characters or fewer, and `tools/call` validates that a submitted name matches `^[A-Za-z0-9_-]+$` and is at most 128 characters.

<Warning>
Copy a tool name from `tools/list`. Never construct one. The readable part is trimmed at an arbitrary point and the digest cannot be derived from anything a client can see, so a hand-built name will not resolve.
</Warning>

Because the digest covers the connection id, two connections to the same provider — two GitHub accounts, two AWS accounts — never collide. Each gets its own distinct alias for the same underlying tool, and each maps server-side to exactly one stored connection.

## What the gateway publishes, and what it holds back

Aggregation is gated by the reviewed static tool names for each connection, and the rules are explicit:

| Connector surface | Published through `/connect/mcp` |
| --- | --- |
| `typed-proxy` | Exactly the tool names in its manifest |
| `compatibility-read` | Only `read-provider-resource` |
| `provider-mcp` | **Nothing** |
| `command-auth` | Nothing — these connectors publish no Receipt tools anywhere; they become CLI configuration inside a worker instead |

Provider-native MCP connectors publishing nothing through the aggregate gateway is deliberate. Their tool lists are discovered from the upstream provider at runtime, so an upstream tool added later would silently become callable across the organization without ever being reviewed. Those tools stay reachable through the per-connection routes (`/connect/tools` and `/connect/call`) — just not through the aggregate endpoint.

Two more rules shape a listing:

- **Write tools appear in `tools/list` only when the token carries `connect:write`.** A read-only token sees a shorter list, not a list with failures in it.
- **One unhealthy connection is skipped with a warning** rather than failing the whole listing, so a single expired connection does not take down every other tool.

Every published tool carries a `readOnlyHint` annotation derived from its access class.

## Setting up a client

The **MCP Gateway** landing page in Organization Settings describes itself:

> Set up an MCP client against this organization, then open a workspace to manage its isolated connections, keys, permissions, and activity.

Below that sits the setup panel, headed **Use connections with Receipt CLI and MCP clients**: "Receipt CLI and the local MCP bridge use a workspace-bound token. The selected workspace is `<name>`; its connections and permissions are isolated from other workspaces in this organization." A badge next to it reads **Default workspace** or **Workspace scoped** so you can see which one you are configuring.

The panel gives five numbered commands, each with its own copy button:

```bash
receipt mcp install codex     # 1. Install the Codex MCP bridge
receipt mcp config codex      # 2. Preview Codex MCP configuration
receipt mcp status codex      # 3. Check the installed bridge (optional)
receipt workspace current     # 4. Confirm the active organization workspace
receipt tools list            # 5. List available tools (optional)
```

If a copy fails, the toast reads "Could not copy the command. Select and copy it instead."

## The workspace Overview

Opening a workspace lands on **Overview**, described as "Connections, LLM keys, and access for `<workspace>`." Three tiles sit above three tabs, and each tile links to its tab:

| Tile | What it counts | Tab |
| --- | --- | --- |
| Open integrations | Distinct providers with at least one `valid` connection | Open integrations |
| LLM keys | Configured bring-your-own-key providers | LLM keys |
| Your access | Your effective role in this workspace | Settings |

The **Open integrations** tab is the same integrations surface as Organization Settings, scoped to this workspace: connecting there writes into this workspace and nowhere else.

## Where the links go

Several gateway routes redirect, on purpose, so a link behaves predictably rather than landing on a page that cannot describe itself.

| Path | Behaviour |
| --- | --- |
| `/organization/settings/mcp-gateway/` | The landing page |
| `.../mcp-gateway/dashboard` | Redirects to the workspace list. There is deliberately no organization-level dashboard: with no workspace open, the page could not say what its figures describe |
| `.../mcp-gateway/integrations/` | Redirects into the current workspace's Overview, falling back to the workspace list when the organization has none |
| `.../mcp-gateway/workspace/` | Redirects to the gateway landing page |
| `.../workspace/$workspaceId/` | Redirects to that workspace's Overview |
| `.../workspace/$workspaceId/connections` and `.../settings` | Redirect to the Overview with the matching tab selected |

The workspace id is a **path parameter, not a search parameter**. That is why refreshing, using the back button, or opening a shared link restores the same page instead of racing a state write.
