## 3. Path and citation hygiene

- **`RELEASE-HANDOFF.md` is cited three times (§1.2, §1.7, Open Question 7) as if it were a repo file. It is not.** It exists only at `dist/receipt-cli-release/v0.1.0-preview.7/RELEASE-HANDOFF.md`, and `dist/` is gitignored (`.gitignore:4`), so it is absent from HEAD entirely. Its content (Bun 1.4.2, "Files to upload") is real, but it is a local build artifact, not something a doc reader can find. Open Question 7 ("both should be updated") is therefore partly moot.
- **`doc/cli/*.mdx` (the "eight pages") do not exist anywhere in this repo.** The report devotes a whole corrections section to them without ever naming the repository they live in. A doc writer following the report will not find them. Same for the prior research `04-public-cli.md` / `05-repo-cli-core.md`.
- **`LOCAL_SETUP.md`** is deleted in the working tree and untracked at `docs/LOCAL_SETUP.md`. The report discloses this in §0.4 and correctly cites `HEAD:LOCAL_SETUP.md`; the cited range `:975-978` is verbatim correct. Still, any published doc should not cite a path that `ls` cannot find.

## 4. Missing or too-thin topics, by assigned scope

**Distribution**
- No mention that the binaries are **ad-hoc signed only** (the report notes `codesign` output in §0.3 but draws no user-facing conclusion). A user who downloads the tarball through a browser instead of `curl` gets a quarantine attribute and a Gatekeeper block; a `curl | bash` install does not. This is the most likely real install failure on macOS and it appears nowhere in §7.
- Exit **137** ("Killed: 9") on launch — documented in the build script as the malformed-signature symptom — is absent from §6 and §7.
- No statement of what an upgrade does to an existing `~/.receipt` session or to a previously installed Codex MCP entry (the README's stale-`kentronai` note is quoted, but the "re-run `receipt mcp install codex` after the binary path changes" consequence is only implicit).

**Targets and URL resolution**
- The `--target <bad-word> --server-url <url>` throw-before-override case (row 12).
- Prod `authUrl` also filtering localhost values (row 11).

**Sessions**
- Behaviour when both `RECEIPT_CLI_CONFIG_DIR` and `RECEIPT_CLI_SESSION_FILE` are set (the latter wins for the active file and suppresses per-target files entirely) is stated in the table but never shown as the CI isolation recipe it implies.
- `readReceiptCliSessionFile` swallows only `ENOENT`; a permission or I/O error **throws** and surfaces as a bare message with exit 1. The report says a bad file "reads as 'no session' rather than an error", which is true only for parse failures and missing fields (`receipt-cli-session.ts:105-110`).

**Commands**
- `mcp serve` is covered but thin: the supported MCP protocol versions and the `Mcp-Session-Id` forwarding get one clause; a client-integration doc needs more.
- `receipt connect <provider>` server-side failure modes beyond 400/503 (e.g. what a user sees when Nango returns a link that never validates) are only covered by the timeout string.
- No worked example anywhere of the full happy path with real output (understandable — no sign-in was performed — but the doc it feeds will need one).

**Environment variables**
- §5 is complete for the public binary as far as I could check; the one gap is that it never says which of these are *safe to set in CI* versus *dangerous* (e.g. `RECEIPT_CLI_SESSION_FILE` pointing at a shared path).

**Exit codes**
- See row 40: the "no other codes exist" claim needs the 137 caveat, and the developer CLI's own `127` (missing Bun, from the `.receipt/bin/receipt` wrapper) is mentioned in §8 but never reconciled with §6's "no other codes exist".
