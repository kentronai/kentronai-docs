- No AWS account ids, ARNs, IP addresses, email addresses, API keys, hosted URLs, AWS profile names, stage names, or named production actors appear in the report. The report references those categories only descriptively ("stage names", "profile default", "named actor") without values.

My masked spot-check found hosted origins and a named AWS profile in `factory-agent-cli` (row 28), an explicit `--profile` instruction in `factory-aws-cli-cookbook:13` (generic, not a value), and a 12-digit account-id placeholder line in `factory-aws-prod-runbook:36` (already classified internal-only). Nothing from those files was copied into this document.

## Missing or too-thin topics (within the report's assigned scope)

1. **The catalog skill is never pointed to by the prompt.** `skills/factory-organization-skill-catalog/SKILL.md` is always added to `repoSkillPaths` (`skill-paths.ts:39-43`), but `resolveCheckedInSkillPathsForPrompt` keeps only the worker skill plus profile-selected refs (`task-prompt-skills.ts:20-25`), and `appendSkillBootstrapLines` names only the worker skill and the first profile skill (`task-packet-summary-skill-lines.ts:31-36`). The catalog skill therefore reaches Codex only as a `CODEX_HOME/skills/<name>` copy plus the one context.md sentence about `receipt/skills/index.json`. The report presents it as "always-selected" without saying it is unreferenced in both prompt surfaces. Docs should not imply the worker is instructed to read it.
2. **Per-skill hosted-detail scan for the "public-safe" subset.** Row 28 shows the internal-only column was inferred, not checked file by file. Before publishing any `skills/` content, grep each candidate for `https://`, `AWS_PROFILE`, `--profile`, `--stage`, and 12-digit numbers.
3. **Non-admin member experience on the Skills page.** The Zero query returns nothing for non-owner/admin members (`org-skills.queries.ts:23-28`), so such a member sees "No organization skills yet" and an "Add your first skill" button whose upload then fails with the admin error. The report covers authorisation but not this UX edge.
4. **Objectives without an org auth context get no organization skills.** `task-packet-writer-core.ts:39-51` gates collection on `state.authContext?.organizationId`; the report says "when the task has an `organizationId`", which hides that the gate is the objective's auth context (relevant to CLI-started or replayed objectives).
5. **Frontmatter block-scalar edge.** Only bare `|` and `>` values open a block (`organization-skills.ts:271`); `|-`, `>-`, `|+` are treated as literal scalars. Worth one line in the SKILL.md contract page since Claude-/Codex-style skills commonly use `>-`.
6. **Prompt-cache key vs. actual system prompt.** `buildAppChatPromptCacheKey` hashes `'You author one organization agent skill from the current user request.'` while the model receives `ORGANIZATION_SKILL_AUTHORING_SYSTEM_PROMPT` (`receipt-chat.service.ts:3510-3511, 3530-3537`; `organization-skill-chat.ts:23-27, 77`). Not user-facing, but it should not be documented as "the system prompt is the cache key".
7. **Tracked file mutated in worktree mode.** `receipt/skills/index.json` is git-tracked, and `materializeOrganizationSkillRegistry` unconditionally rewrites it in every task workspace (`workbench-projection.ts:436-439`). Remote-patch exclusion covers the OpenSandbox path; the report does not say what happens to the dirty tracked file in local worktree mode (Open Question 8 only asks whether to keep the placeholder).
8. **CLI/Runtime visibility of organization skills.** The report covers `profileSkills` in `receipt factory agent context` but not whether any CLI/API surface lists the organization skill registry for a run (count/hash); readers documenting "auditability" will ask.
9. **`setOrganizationSkillEnabledAction` message on disable.** The action throws "Archived skills cannot be enabled." for any toggle on an archived row, including a disable request (`organization-skills.server.ts:284`). Trivial, but the string is misleading if it ever surfaces through the server function.
