## 4. Missing or too-thin topics in the assigned scope

1. **Authentication on the runtime's core routes is never stated.** The report documents auth for `/connect/*` (JWT scopes) and `/receipt-debug/*` (bearer + scope), but never says what protects `POST /agents/:id/jobs`, `/jobs/*`, `/memory/*` and `/chat/*`. The answer is: nothing at the route layer — they are unauthenticated and rely on network placement behind the gateway (`service-graph.ts:92-98` marks `/runtime/*` private). For a public HTTP API reference this is the single most consequential omission, and R17's "an unknown agent id still gets 202" is much sharper once paired with it.

2. **The Zero mutate receipt-write path (R33/R34) is not merely mis-stated — it is undocumented.** Server-pass Zero mutations append hash-chained receipts with hand-rolled SQL, outside `postgresReceiptStore.append` and therefore outside `dispatchReceiptAppendCallback`. Whether that path triggers the `receipt_projection_work` trigger (it does — the trigger is on `receipt_receipts`) but skips the in-process append callback is exactly the kind of detail the "receipts are the only truth" chapter needs.

3. **The server-side WebSocket layer is a blank.** §3 establishes that `/factory/live` is a WebSocket and that the browser client requires WebSocket, but nothing describes the server side: the `websocket` handler passed to `Bun.serve` (`bootstrap.ts:3742`), the upgrade handshake at `register-factory-api-routes.ts:636-638`, subscription framing, or whether WS connections get a keepalive at all (the 5 000 ms ping is SSE-only). The report's own §11 suggested page "Live events (SSE and WebSocket)" cannot be written from what is there.

4. **`packages/receipt-dst` gets one clause.** It is named in the "zero commits" list and credited with overriding `receipt.core.randomBytesSource`, but the deterministic-simulation package itself — its API, what it replays, how it relates to the Factory sims in §8.4 — is never described, despite `receipt dst` appearing in the §8.7 feature table.

5. **Three Zero synced queries and three Connect PATCH routes are absent from the inventories** (R32, R21). The missing queries (`sessionMessagesBySessionStream`, `memoryEntriesByScope`, `memoryAccessesByScope`) are the browser's whole read path for session messages and memory — a visible gap given that §1.8 lists `receipt_memory_entries` and `receipt_memory_accesses` among the default-published tables but never says what reads them.

6. **`zeroPublication: "never"` is used but not defined.** `receipt_session_recap_projection` is flagged `never` in §1.8 with no explanation of how `never` differs from `internal` in effect, or why a recap projection needs the stronger mode.

7. **`hints` are described only as "non-authoritative".** Given the report correctly emphasises that hints are excluded from the hash, the natural follow-up — what actually writes hints in production, beyond `eventId` — is never answered, though §1.1 asserts they exist for "indexes, tracing, or idempotency".

8. **The web app's own SSE keepalive is unmentioned.** `/api/receipt-trail/events` wraps the proxied stream in `withSseKeepAlive` (`apps/start/src/routes/api/receipt-trail/events/route.tsx:5, 45`), so a client sees two independent keepalive regimes. §3 documents only the runtime's 5 000 ms ping.

9. **`sdk/agent-spec-loader.ts` sits inside the SDK but outside the barrel** (R36). Since it is the mechanism by which remote actions resolve a spec, the "eight exports" framing understates the SDK's real public surface and hides the coupling between §7.1 and §7.3.

10. **Runtime→web/Slack/Teams client semantics.** §10 lists which endpoints each surface calls, but nothing covers timeouts, retries, or `resolveReceiptServerUrl` resolution — the operational half of the API contract.
