## Missing or too-thin topics (within the report's assigned scope)

1. **Disconnect never removes discovered agents.** The inventory stream has only `scan_requested`, `scan_completed`, and `scan_failed` events (`packages/receipt-app/src/services/agent-inventory.ts:73-92`); a `scan_completed` replaces agents *for that connection id* only, and Disconnect is a Receipt Connect action that appends no inventory event (grep for `agent_inventory` in `apps/start/src/lib/frontend/receipt-connect/*.ts` and `receipt-connect-connections.ts` → 0). After a provider is disconnected, its previously discovered agents therefore stay in the inventory and in the dashboard counts indefinitely, with no way to purge them from the UI. This is a material operational caveat for the docs and belongs next to §2.11.
2. **GCP OAuth scopes are stated in the repo.** The report says the repo "does not enumerate the GCP IAM permissions" and lists GCP "Extra config: none". The `google` manifest requests `https://www.googleapis.com/auth/cloud-platform.read-only` and `https://www.googleapis.com/auth/devstorage.read_only`, and its `credentialHint` says which Google APIs must be enabled on the OAuth client's project and warns that `cloud-platform.read-only` is a restricted scope whose consent screen must be verified before production (otherwise refresh tokens keep the seven-day testing limit) (`packages/receipt-app/src/integrations/nango/slugs/google/provider.json`, `setup` block). Docs need this; it partly answers Open question 5.
3. **The three cloud connectors are also ordinary Global Integrations with proxy tools.** `azure` publishes `list-subscriptions` and `query-resources`; `gcp` publishes `list-projects`, `get-project`, `list-storage-buckets`, `list-compute-instances`, `list-compute-zones` (same manifests, `apiProxy.tools`). The report treats AWS/Azure/GCP only as Agent Registry credentials; the Catalog page should say that connecting them on Global Integrations (connection `default`) exposes these read tools to chat/MCP, independently of the `agent-registry` connection.
4. **What the inventory persists and shows to every member.** Rows carry the Bedrock agent's `instruction` (its system prompt) as `purpose`, IAM policy summaries, named data-store ARNs, and CloudTrail principal ARNs/user names, stored in `receipt_entity_projection.row_json` and in receipt bodies and returned to any org member by `listAgentInventoryAction`. Open question 2 covers member visibility of owners/findings; the prompt-text and ARN retention deserves an explicit privacy note.
5. **Concurrent scans.** Nothing prevents two admins from scanning at once; receipts serialise only through the 5-attempt chain-conflict retry (`agent-inventory.ts:255-289`), and each run replaces the whole projection (`:306-377`). Worth one sentence under §2.10.
6. **Duplicate RCA number.** `docs/agent-fix-checklist.md` has two headings numbered RCA-522 (`:20813` Nango catalog pin, `:21118` CLI onboarding). If public docs cite "RCA-522" for the Azure patch, they should cite the heading text, not the number.
7. **Connectable-card count.** The report equates the audit's 63 runtime connectors with connectable cards; no test pins the card count and one card can map to several connectors (row 14). Use "about 60" in prose, as the "What to claim" section already does.
