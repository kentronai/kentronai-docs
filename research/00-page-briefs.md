
# TAB: Guides

## GROUP: Start here

### introduction — What Receipt is
purpose: Orient a new reader on what the product does and settle the naming question before anything else.
sources: 01, 03, 03c, 07, 09
substance: Every chat turn first runs a classification-only router model call returning one of three decisions: `chat` (a second profile-aware pass writes the answer directly), `organization_skill` (authors a new org skill), or `factory` (enqueues a durable background objective whose progress streams back into the thread). An unparseable router call fails closed to `factory`. Every turn is recorded as hash-chained receipts you can replay. Naming, code-verified and nothing more: app.kentron.ai is the hosted app origin used as the trusted origin and auth base; https://docs.kentron.ai/introduction is hard-coded as the sidebar footer 'Docs' link; kentron.ai is also the staff email domain gating an internal admin console, which is operator tooling and not a customer surface. The shipped UI titles itself 'beetle.run' (browser title, navbar brand label) and the assistant persona in chat prose is 'Beetle'; the contracting entity in Terms, Privacy and Acceptable Use is 'The Unreal Compound SA de CV'. No code states a corporate relationship between these names — a human owner must supply that sentence before this page ships. Also maps the sidebar as it actually renders: New, Beetle Chat, Slack, MCP Gateway, Model Gateway, Agents, the admin areas visible only to owners/admins, the Docs footer link and the 'Beetle runners' widget.

### getting-started/your-account — Create and manage your account
purpose: Get a brand-new visitor signed in, and cover the account and security settings they will need afterwards.
sources: 01
substance: Sign-up at /auth/sign-up: email must match a basic address pattern, password 8–128 characters, confirm must match; errors are 'Please enter a valid email address', 'Password must be at least 8 characters', 'Passwords do not match'. In cloud mode a 6-digit email OTP follows, valid 5 minutes with 5 attempts, stored hashed; 'You entered too many incorrect codes. Request a new one to continue.' Immediately after the user row is created the server provisions an organization named '<Display Name>'s Workspace' (name derived from the email local part when empty), writes its billing baseline (plan free, 5 seats) and grants a one-time $5.00 platform credit — once per user, not per organization. The redirect target is /chat; there is no onboarding wizard in cloud mode. /login is a permanent redirect to /auth/sign-in. Password reset is an emailed OTP code, not a link, and revokes all other sessions. Accounts that already have TOTP see a 'Two-step verification' step at sign-in; there is no enrollment surface in the product, so 2FA cannot be turned on today. /settings covers avatar (JPG/PNG/WEBP/SVG, 10 MB, 'File exceeds limit of 10MB.'), display name (32 characters), email change (disabled entirely in self-hosted builds) and interface language (en, es, he). /settings/security covers connected login methods with the guard 'You must keep at least one login method connected.', change/set password, and active sessions with 'Revoke other sessions'. Sessions last 7 days with a 1-day sliding refresh; up to 10 concurrent device sessions.

### getting-started/your-first-chat — Your first chat
purpose: Teach the composer as it actually behaves, including which controls do nothing on a direct answer.
sources: 03, 03c
substance: The empty state is 'Hello, <name>' / 'What would you like to explore?'. On a new chat the placeholder cycles through 25 'Ask Receipt to …' prompts; inside a thread it is 'Ask anything'. The submit control reads Send message / Sending... / Stop generation / Error and stays clickable as a stop button while a response streams. The `+` menu contains: Attach files (label becomes 'Attach files (max reached)' at 10 files), Study Mode (the only shipped mode — pins openai/gpt-oss-120b, injects a study system prompt, and disables all provider-native tools; disabled with 'Study Mode is enforced by your organization' when an org enforces a mode), Max (rendered only when the model has a distinct max context window; the default mode is `standard`), and a Tools checkbox group. State plainly that the direct-answer path sends `tools: {}` and `activeTools: []` to the model, so toggling Web Search changes nothing on a direct answer — real tool work happens through background runs. The model and reasoning-effort pickers are not mounted, so the model is fixed at the default and reasoning effort at that model's default. The Context hover card shows Input, Output, Reasoning, Cache read, Cache write from the last persisted assistant usage, and a Total cost row only when the org used its own provider key or the operator enabled cost display. Thread titles are auto-generated from the first message (3–4 words, capped at 8 words and 50 characters); renaming a thread permanently disables auto-titling. A paste of 2 000+ characters becomes a `pasted-text-YYYY-MM-DD-HH-MM-SS.txt` attachment when embeddings are enabled. Send is blocked while uploads are pending or the context limit is reached.

### getting-started/background-runs — Background runs
purpose: Explain what happens when a turn becomes a durable objective, and how to follow or stop it.
sources: 03, 03c
substance: When the router chooses `factory`, Receipt posts a job with kind `factory.run`, lane `chat`, sessionKey `factory-chat:<stream>`, maxAttempts 2 and config `{maxIterations: 1, maxToolOutputChars: 6000, memoryScope: 'factory-chat:auto', workspace: '.'}`, records a progress receipt reading 'Beetle queued job <jobId>.', persists an empty assistant shell so the thread can show progress, and settles the HTTP request at 202. The thread renders a progress panel with an elapsed timer and expandable 'Progress details'; raw runtime text is humanized ('Recorded reasoning for iteration N' → 'Captured reasoning', 'planned factory.dispatch' → 'Planned background run', 'factory.dispatch: started' → 'Started background run', 'reconnected to the beetle runtime' → 'Reconnected to Beetle', 'tracking beetle objective …' → 'Tracking the objective') and only the last 6 de-duplicated steps are shown. A 'Computer preview' button opens Computer Logs — 'Live output from the workspace computer', a log search, an Errors filter, lines prefixed `$ ` (stdout), `[err] ` (stderr) and `> ` (activity), at most 80 buffered lines, and the empty states 'Beetle computer offline' and 'Computer is active; waiting for shell output.' Because objective state syncs from a projection keyed by objectiveId, you can close the tab and return to a finished answer; `/chat?objective=<id>` re-attaches a run to its thread. Stop closes the stream and cancels the objective and every active job, appending 'This task is stopped.'; if cancellation fails the banner reads 'Stopped the response, but could not cancel the agent run.' A failed run renders 'Beetle stopped before completing this response.' with Status and a reason compacted to 400 characters, plus a distinct message when the sandbox runtime was unavailable. Naming a connector in a prompt does not by itself force a background run — only a request for your own private or current data does.

## GROUP: Working with Receipt

### guides/files-and-attachments — Files and attachments
purpose: Set exact expectations for what can be attached and how a file changes a later answer.
sources: 03
substance: Accepted extensions: .pdf, .jpeg, .jpg, .png, .webp, .svg, .txt, .html, .htm, .xml, .xlsx, .xlsm, .xlsb, .xls, .et, .docx, .ods, .odt, .csv, .md, .markdown, .numbers, with the matching MIME list. Limits: 10 MB per file and 10 files per message. Validation order matters: a matching MIME type accepts immediately, a non-matching non-octet-stream MIME rejects immediately, and the extension is only consulted when the MIME is empty or application/octet-stream. Error strings: 'File type is not supported for markdown conversion', 'File is empty' (rewritten server-side to 'Uploaded file is empty'), 'File exceeds limit of 10MB', 'Missing file field'. Self-hosted deployments without a markdown worker return 'This self-hosted instance only accepts direct text attachments until the markdown worker is configured.' Plain-text-family files (txt, md, markdown, csv, html, xml) are read inline; everything else goes through a markdown conversion worker with a 20 000 ms timeout ('Markdown conversion timed out', 'Failed to convert uploaded file'). Images and PDFs are handed to the model natively only when that model declares image or PDF input; every other file uses retrieval — the markdown is split into ~1 600-character paragraph-aware chunks with 260 characters of overlap, capped at 140 chunks per document, and on your next question up to 8 chunks or 12 000 characters are appended after your text under a 'User-provided attachment context' header. When nothing is indexed the whole stored markdown is truncated to 2 000 characters per file instead. Embeddings are skipped entirely when the organization's provider key is not OpenAI-compatible, and the upload still succeeds. File uploads are not plan-gated in this release.

### guides/managing-conversations — Editing, branching, and finding messages
purpose: Cover the conversation-tree mechanics and search, which are the two things users get wrong.
sources: 03
substance: Messages form an immutable tree keyed by parentMessageId with a deterministic canonical path — never 'most recent wins'. Editing a user message or regenerating a response creates a sibling branch reachable through the n/m pager (Previous branch version / Next branch version); only user messages on the current canonical path are editable, and regeneration always anchors to a user message even when you trigger it from an assistant reply. There is no per-message delete and no explicit fork action — branching is what edit and regenerate do; deletion is thread-level from the sidebar. Every write carries an expected branch version: a stale-but-lower version is rebased once and retried so an older tab keeps working, and an unrecoverable conflict surfaces 'This chat changed in another tab or session. Refresh and try again.' Editing or regenerating during a live stream is refused server-side. Sidebar: New Chat, Chat History, Projects, Search chats; date groups Pinned, Today, Yesterday, Last 7 Days, Last 30 Days, Older; per-thread Rename, Copy link, Pin/Unpin, Delete with toasts 'Thread renamed', 'Thread title cannot be empty', 'Failed to delete thread' — and note that the delete-success toast reads 'Objective deleted'. Per-thread status pills are Pending, Generating and Error with their descriptions. Search: Cmd/Ctrl+K opens the palette globally, the sidebar entry opens it in search-only mode; 120 ms debounce, 20 results by default and 30 maximum, a query over 200 characters fails as too long, and body search requires at least 2 characters. Content search scans projected session messages, so messages on hidden branches are findable; selecting one activates the whole root-to-leaf branch path in a single guarded mutation, scrolls the message into view and wraps matches in highlight marks, skipping code, pre, input and textarea.

### guides/receipt-in-slack — Receipt in Slack
purpose: Install the Slack app and set correct expectations for what it does and does not do.
sources: 03e
substance: Installation is a direct Slack OAuth v2 flow, not an integration-provider flow. The sidebar 'Slack' entry opens /api/slack/install, which requires a signed-in org admin — 401 'Sign in and select a workspace before installing Slack.' and 403 'Only workspace admins can install Slack.' The install state is HMAC-signed with a 10-minute TTL; a stale one produces 'Slack installation state is invalid or expired. Start again from Receipt.' Scopes requested: app_mentions:read, channels:history, chat:write, reactions:write, users:read, users:read.email — no user tokens, no commands scope, no message.im. Success reads '@receipt added to <team name>!' / 'Go to any channel, type /invite @receipt, then mention @receipt to get started.' The Slack-directory ('Add to Slack') path is implemented: the bot token is encrypted and parked for 10 minutes, and an org owner or admin claims it at /auth/slack-install with the exact errors for expired, already used, already connected elsewhere, forbidden and no-organizations. One Slack team belongs to exactly one Receipt organization. Per-message identity: an existing link runs as that Receipt user; otherwise Receipt resolves the Slack email and matches an org member, and failing that issues a signup link — with the 'Receipt needs access to your Slack email…' warning when the email is unavailable and the seat-capacity refusal when the workspace is full. Runtime behaviour: a mention, or an untagged reply in an already-activated thread, adds an :eyes: reaction and posts the ack ':hourglass_flowing_sand: <@user> *Working on it…*' / '_I'll post the result in this thread._' Everything afterwards edits that one message. Progress posts appear only on phase changes mapped to friendly labels ('Checking the connected data…', 'Reviewing the results…', 'Preparing the answer…'), throttled to one per 20 seconds and capped at 12 — internal running phases deliberately produce no message. The terminal message carries a status label ('Completed in 6s', 'Failed after 1m 05s', 'Canceled after …', 'Blocked after …'), markdown down-converted to Slack mrkdwn with tables flattened, truncation at 2 800 characters, images as blocks, and a 'View Receipt' link — no internal ids are printed. The overall deadline is 10 minutes with a message that deliberately never claims completion. Funding: an organization OpenAI key is validated live with an 8-second timeout, otherwise a platform-credit reservation is taken, with the exact refusals for no credit, exhausted credit and unverifiable key. Not implemented: slash commands, buttons and modals, DMs, app home, file uploads, message shortcuts.

## GROUP: Accounts and tenancy

### platform/organizations-and-workspaces — Organizations and workspaces
purpose: Separate the two tenancy concepts that in-product copy conflates, and cover managing both.
sources: 01, 02, 10
substance: An organization is the billing and membership tenant. It is created automatically at signup as '<Display Name>'s Workspace' (derived from the email local part when the name is empty), capped at 10 per user with the message 'You can create up to {max} organizations.', and created manually from the sidebar switcher ('Create organization' / 'Enter a name.' / field 'Organization name' / placeholder 'Acme'). Anonymous users cannot create one. The active organization lives on the session row, and the switcher shows 'Loading organizations...', 'No organizations found', 'Switching...' and a member count per row. Its general settings page carries a logo (JPG/PNG/WEBP/SVG, 10 MB) and an organization name capped at 64 characters. A Receipt workspace is a different thing: the credential and authorization boundary used by the MCP Gateway, Receipt Connect and the CLI. Every organization gets a deterministic Default workspace (id ws_<md5(organizationId)>, name 'Default', slug 'default') that cannot be deleted — the server answers 409 'the Default workspace cannot be deleted', and any workspace holding connections must be emptied first ('workspace connections must be removed before deleting the workspace'). A hidden global-scope row (ws_global_<md5(organizationId)>, reserved slug) also exists and is excluded from every workspace list. The Workspaces page — 'Isolate connected accounts, action permissions, CLI sessions, and MCP tools inside your organization.' — offers New workspace (name max 80, 'Workspace names help people choose the correct authorization boundary.'), Rename, Share, and a two-step Delete that requires typing the workspace name exactly ('This is permanent. Type the workspace name below to delete {name} and revoke its credentials for every agent using it.'). Creating a workspace deliberately does not switch into it, and clicking a row opens the MCP Gateway workspace overview. Workspace state is event-sourced into organizations/<orgId>/workspaces/<workspaceId> and projected. Effective role: an organization owner or admin is treated as owner/admin in every workspace regardless of the workspace member row, and any organization member can open the Workspaces page because it matches the MCP-gateway path rule.

### platform/members-roles-and-invitations — Members, roles, and invitations
purpose: Document who can do what, how people are invited, and what happens when seats run out.
sources: 01, 02
substance: Roles are Better Auth's defaults: owner (organization update and delete, full member and invitation control), admin (organization update, full member and invitation control), member (read only). Receipt's own admin predicate treats owner and admin identically and tolerates comma-separated role strings. Settings access, which surprises people: every page under /organization/settings is owner/admin-only with one exception — paths matching the MCP-gateway rule, which include /organization/settings/workspaces, are open to any member. A denied user is silently redirected to `/` with no access-denied screen; while the role resolves the page shows 'Checking workspace access', and the client-side gate fails closed. The Members page — 'Manage organization members, pending invitations, permissions, and access status.' — has columns User, Email, Role, Status, a filter box, and status badges active | pending | restricted with tooltips ('Invitation has not been accepted yet.' and the access reason code, or 'Access is restricted.'). Row actions: Change role (Admin or Member only — owner is not selectable and the last owner is protected), Remove member, and Cancel invitation on pending rows; the current user's own row menu is disabled. The invite dialog sends up to 10 addresses per batch, one API call per address, with a per-row role select defaulting to member. Invitations expire after 48 hours; the email subject is 'You're invited to join {organizationName}' and links to /auth/accept-invitation/<id>. On self-hosted deployments with no mail transport nothing is emailed and the dialog shows copyable /auth/sign-up?invitationId=<id> links instead. Accepting pre-fills and locks the email field ('This invitation is tied to this email address.'), and a mismatch gives 'Use the email address that received the invitation to continue.' Seats: capacity counts active members plus pending invitations plus the new invite against the entitlement seat count, and an overflow invite fails with HTTP 403 and the message 'Only {n} users can access this workspace.' Over-limit organizations are flagged, with the UI strings 'Seat allocation', '{active} of {total} seats', 'Over seat limit' and 'No paid seat assigned'. A second invitation kind exists for sharing one workspace with an existing organization member: a signed `wsinv_` token with a 48-hour TTL, which returns 'new_user' when the email is not already a member.

purpose: Cover the model catalog, provider accounts, and the org-level controls over both — with their real enforcement status.

The provider gallery shows 32 catalog tiles (AWS Bedrock, Google Vertex, Google Gemini, Azure OpenAI, Azure AI Foundry, Microsoft Foundry, OpenAI, Databricks, Cloudera, Cohere, Snowflake Cortex, OpenRouter, AI21, Anthropic, AWS Claude Platform, AWS Bedrock Mantle, DeepInfra, Groq, Mistral AI, ElevenLabs, Deepgram, Cartesia, Smallest AI, Perplexity AI, Together AI, xAI, Baseten, SambaNova, AWS SageMaker, Cerebras, Wafer, Self-Hosted Model), of which only `openai` and `anthropic` are executable — every other tile is a clickable catalog preview and the server refuses to save one with 'This provider is a catalog preview and cannot be configured yet.' Compliance flags: 'Require ZDR (Zero Data Retention)' restricts model selection to catalog models marked zero-data-retention and gates tool access — it is bypassed for a model whose route provider has an active executable organization key, and it does not suppress application error telemetry; 'Require organization provider key' has a toggle but nothing in the request path reads it, so do not document it as enforced; 'Enforce Study Mode' pins openai/gpt-oss-120b, injects its prompt and disables provider-native tools for openai, anthropic, google and xai. Warn about the inverted toggle semantics: on /models/$providerId a checked switch means enabled, while in Model Controls a checked switch means disabled. All model-policy denials return HTTP 403 with machine reasons policy_denied:provider, :model or :compliance.

### platform/bring-your-own-key — Bring your own key
purpose: Add an organization provider key correctly and understand what it changes at request time.
sources: 02, 03, 09
substance: /organization/settings/byok is 'Optional: use your organization's encrypted provider keys instead of platform credit (Bring Your Own Key).' The runtime supports OpenAI and Anthropic, but the page renders OpenAI only at this checkout — Anthropic is hidden as a presentation decision and any key already stored for it stays encrypted and honoured. A configured key shows as a masked value with the input disabled until it is removed; the button reads 'Save key' or 'Remove key'. Validation is two layers and both must pass: format (OpenAI keys must start with `sk-`, Anthropic with `sk-ant-`, with those exact messages) and a live non-mutating call — GET https://api.openai.com/v1/models with a bearer, or GET https://api.anthropic.com/v1/models?limit=1 with x-api-key and anthropic-version 2023-06-01 — bounded at 10 000 ms, where 401/403 gives a non-retryable 'Unable to connect to {provider}. Verify that your {provider} API key is valid.' and any other failure gives a retryable 'could not validate this API key right now' message. Validation runs before encryption and persistence, so a revoked key never becomes durable state. Storage: table org_provider_api_key keyed (organization, workspace, provider), AES-256-GCM with a 12-byte IV and key version 1, wrapping key from BYOK_ENCRYPTION_KEY_B64 which must decode to exactly 32 bytes ('Missing required environment variable BYOK_ENCRYPTION_KEY_B64.', 'must be valid base64.', 'must decode to exactly 32 bytes.'); only a 12-hex-character fingerprint is ever logged. The ZDR confirmation dialog ('Disable ZDR for this provider?' / 'Save key and disable ZDR') is literal behaviour: an active executable organization key sets a compliance bypass for that provider. Rotation warning: there is no re-encryption routine anywhere, and decryption hard-fails on any other key version — rotating BYOK_ENCRYPTION_KEY_B64 makes every stored key permanently undecryptable and each organization must re-enter its keys.

### platform/integrations — Receipt Connect and the connector catalog

### platform/connection-scopes — Where a connection lives
purpose: Explain why an app connected in one place is invisible in another — the single most misunderstood behaviour.
sources: 10, 02, 01
substance: Connections are stored per workspace, never per organization, and three workspace-shaped scopes exist. The Default workspace (ws_<md5(organizationId)>) is created for every organization. Named workspaces are created by users and are isolated authorization boundaries with their own connections, provider keys, members and activity. A hidden Global scope (ws_global_<md5(organizationId)>, reserved slug) is stored as a workspace row but excluded from every list and never selectable. Who reads which: Organization Settings → Integrations writes into the Global scope; MCP Gateway → workspace → Open integrations writes into that workspace; web chat reads capabilities from the Global scope only; the CLI and MCP clients use the workspace bound into their session token. That is exactly why an app connected for chat does not appear in `receipt tools list`, and why a workspace connection does not help chat. The reason is recorded in the code: those are different audiences, and previously resolving both to Default meant connecting an app for chat also connected it for anyone using Default with an MCP client. Legacy connections tagged with only an organization are read-repaired into the Global scope, not Default. Authority levels: workspace membership is required to read; workspace mutation authority (workspace owner or admin, falling back to organization owner or admin) is required for connection lifecycle and permission changes, because those are workspace administration rather than ordinary runtime operations; organization owner or admin is required to create a workspace. Token shapes differ too: the web app mints a 10-minute token carrying connect:read and connect:write and exchanges it at /connect/workspaces/:id/token for a workspace-bound token, while a CLI session token carries connect:read, connect:write and connect:credential for 12 hours and is bound to the workspace you last selected with `receipt workspace use`.

### platform/manage-tools-and-permissions — Manage tools and permissions
purpose: Control exactly which operations a connection exposes, and understand the fail-closed write rules.
sources: 10
substance: The Manage tools dialog is titled '{integration} · {connection}. Every published operation is controlled by this {organization|workspace} allowlist.' and splits operations into 'Read operations' and 'Write and delete operations', each row a switch reading 'Allowed' or 'Never allow'. Access classification happens before anything runs and fails closed: if any declared endpoint method is POST, PUT, PATCH or DELETE the action is a write; if endpoint metadata exists with no mutating method it is a read; if there is no endpoint metadata at all, only a conventional read name counts as a read (get, list, search, find, read, fetch, lookup, whoami, who-am-i, check, describe as a prefix) and everything else is treated as a write. For provider MCP tools, a `readOnlyHint` annotation is authoritative and the name heuristic applies only when it is absent. A write executes only when both gates pass: the caller's token carries connect:write — otherwise HTTP 400 'integration action '<tool>' requires connect:write' — and the action is enabled in the connection's allowlist. A tool that does not exist and a tool that is disabled return the identical 404 'integration action not found or disabled', so a caller cannot probe for hidden tools. Policy semantics: a version-1 policy (never edited) keeps reviewed read actions enabled by default and writes only when explicitly listed; any admin save writes a version-2 policy, after which only listed actions are enabled including reads, and an empty version-2 list exposes nothing. Web chat detects exactly that state and answers '{Provider} is connected in Global Integrations, but you don't have access to any enabled {Provider} tools right now.' with a link to Manage tools. Unknown action names are rejected with 'integration action '<name>' is not available'. GitHub connections carry a second policy with mode `all` or `selected`: under `selected`, identity and repository-list endpoints are allowed but the response array is filtered to the selected repositories, a request to an unselected repository returns 403 'GitHub repository '<owner/repo>' is not selected for this connection', and any other GitHub path returns 'this GitHub endpoint is unavailable while selected repositories are enforced'; discovery pages at 100 per page up to 1 000 repositories with a truncation flag. Atlassian connections resolve the site automatically and fail explicitly when the connection can reach more than one site. Every gateway call writes a `tool.called` receipt and, on success, a `tool.observed` receipt on receipt-connect/gateway/<orgId>/<workspaceId>, with output truncated at 2 000 characters and a truncation flag; a failed call records only `tool.called` with its error.

### platform/mcp-gateway — The MCP gateway
purpose: Point an MCP client at Receipt and understand which tools the gateway publishes and which it holds back.
sources: 10, 04
substance: Receipt exposes one aggregate MCP server at POST /connect/mcp. Server identity is {name: 'receipt-connect', version: '1.0.0'} with capabilities {tools: {listChanged: false}}; supported protocol versions are 2025-11-25 and 2025-06-18, and an unknown requested version falls back to the first. Methods are initialize, notifications/initialized (202, no body), tools/list (a cursor parameter is rejected) and tools/call; anything else returns JSON-RPC -32601. ### cli/overview — The `receipt` CLI
purpose: Establish which binary this tab documents and the parsing behaviour that trips people up.
sources: 04, 05, 03b
substance: There are two different programs named `receipt`. This tab documents only the released binary. Its entire command surface is `setup`, `workspace`, `tools`, `mcp`, `connect`, `import`, `observe` and `--version`; it has no `login`, `logout`, `whoami`, `run`, `jobs`, `memory`, `debug` or `factory`. Dispatch order, and its consequences: `tools`, `mcp` and `workspace` are matched before the help check, so `receipt tools --help`, `receipt mcp --help` and `receipt workspace --help` do not print help — they try to run and, signed out, fail with a not-signed-in error; only `receipt --help`, `receipt help` and `receipt connect --help` print usage. Flag parsing: `--flag value` consumes the next token unless it starts with `--`, so `receipt connect --no-open status` sets no-open to the string 'status' and still opens a browser — put boolean flags last or use `--flag=value`. A bare `--` ends flag parsing, repeated flags accumulate and the last value wins. Errors print to stderr and set exit code 1; successful output goes to stdout.

### develop/architecture — Processes, roles, and routing
purpose: Give a developer the runtime topology: what runs, what listens, and how a request reaches it.
sources: 07, 08
substance: One runtime image runs in five roles selected by RECEIPT_PROCESS_ROLE: `api` is the only role that binds an HTTP port (default 8787) and the only role that runs heartbeats; `driver` registers the job-driver function; `worker-chat` (default concurrency 4) registers job execution plus the remote agent-action worker; `worker-control` (concurrency 1) adds the objective watchdog; `worker-codex` (concurrency 1) handles computer work; an unknown or missing value maps to `all`, which registers nothing. Non-API roles never open a socket and park forever rather than exiting. Call graph: browser → gateway → web app or runtime; the web app calls the runtime for POST /agents/factory/jobs, job control, GET /jobs and GET /receipt/stream; the runtime's api role begins a driver RPC, the driver begins a worker RPC, and the worker executes and settles; workers reach the sandbox controller for computer execution; every role talks to Postgres. ### develop/receipts-and-streams — Receipts, chains, and streams
purpose: Explain the state model precisely enough that a developer can verify, fold and fork a chain.
sources: 07
substance: A receipt is `{id, ts, stream, prev?, body, context?, hash, hints?}`. Two fields are routinely confused: `context` is authoritative receipt scope (actor, tenantId, organizationId, objectiveId, taskId, jobId, runId, branch) and is hashed; `hints` are transport metadata for indexes, tracing and idempotency and are not hashed. The hash is sha256 over canonical JSON of id, ts, stream, prev (null when absent), body and context, where canonicalization sorts keys and rejects undefined, bigint, functions, symbols, non-finite numbers, circular structures and non-plain objects by name. Ids are `<ts in base36>-<8 random bytes hex>` from an overridable entropy source, which is what makes deterministic simulation replayable. `verify(chain)` returns `{ok: true, count, head}` or `{ok: false, at, reason}` with reason 'broken prev' or 'hash mismatch'. The runtime serializes execution per stream, caches a snapshot and folds only the suffix while the cached tail hash still matches, refuses to replay a corrupt chain with 'Receipt runtime refused to replay invalid chain for stream '<s>': <reason> at index <n>', deduplicates a whole command when its eventId hints already exist, and enforces optimistic concurrency with 'Expected prev hash <x> but head is <y>'. Branching: fork saves branch metadata only and copies no receipts, refusing with 'Cannot fork <stream> at <n>; valid range is 0..<len>', 'Branch '<name>' already exists' and 'Stream '<name>' already has receipts'; reads materialize a branch by loading the parent prefix and re-linking and re-hashing the branch's own receipts on top, and a cycle throws 'Branch cycle detected for stream '<stream>''. Verified stream families: `jobs` and `jobs/<jobId>`; `factory/objectives/<id>` and `.../steps/<taskId>`; `memory/<safe-scope>`; `eval/runs/<runId>`; `computer_use/sessions/<id>`; `agents/factory/<repoKey>/receipt` with `/sessions/<chatId>` and `/objectives/<id>` beneath it; `apps/start/<repoKey>/app-chat/sessions/<threadId>`; the generic `<base>/runs/<runId>` and `<runStream>/sub/<id>`; and `__meta/branches` for branch metadata. Projections — receipt_streams, receipt_receipts with its uniqueness constraints, receipt_branches, receipt_projection_offsets, receipt_change_log and the derived tables — are disposable read models rebuildable from replay, never the source of truth. Tenancy: the resolved data directory is hashed into a schema name unless an explicit schema is configured, and every pool pins its search_path.

### develop/jobs-and-durable-execution — Jobs, lanes, and durable execution
purpose: Let a developer enqueue work correctly and reason about leases, retries and recovery.
sources: 07
substance: There are four lanes — chat, collect, steer and follow_up — and six job statuses: queued, leased, running, completed, failed, canceled. Every document listing three lanes is wrong. Lifecycle receipts: job.enqueued, job.leased, job.heartbeat, job.progress, job.completed, job.failed, job.canceled, queue.command, queue.command.consumed and job.lease_expired, with reducer invariants that a lease is ignored unless the job is queued, a heartbeat promotes leased to running only for the matching worker and attempt, and any non-enqueue event for an unknown job throws an invariant error. Singleton semantics: the default is `allow`; an explicit jobId that already exists returns the existing job unchanged, which is the enqueue-idempotency contract callers rely on; with a session key, `cancel` sends an abort command to every active job on that key, and `steer` sends a steer command to the most recent active job and returns that job instead of creating a new one. maxAttempts is clamped to 1..8. Payload kinds and their routing contracts: factory.dispatch, factory.run, factory.integration.publish, factory.integration.validate, factory.objective.audit, factory.objective.control, factory.objective.watchdog, factory.task.monitor and factory.task.run — all but the watchdog require an authContext with a userId and organizationId. Only four agent ids have registered handlers (factory, factory-control, factory-monitor, codex); posting to any other agent id still returns 202 and appends job.enqueued, but nothing will ever execute it. Durable execution: enqueue → dispatch outbox → driver RPC → worker RPC → settlement, with a delivery-generation dispatch key that advances when a previous promise is terminal (bounded at 32 generations), a driver that deliberately does not lease the job, and a worker that leases, checks abort, takes a start fence, races execution against a heartbeat loop and timeout, then settles under an attempt fence with storage retries. The failure statuses that appear in a job result are settlement_conflict, stale_attempt, lease_lost, terminal_state, canceled, execution_timeout and failed. Lease policy: 300 000 ms by default, 900 000 ms for objective control and for codex work (extended by the payload timeout up to an hour), execution timeout is the lease minus 1 000 ms, and the heartbeat cadence is derived to give two renewal opportunities before the fence fires. Three recovery loops run independently: a queued-job redrive (default every 15 000 ms after a 5 000 ms startup delay, with minimum-age and cooldown guards and an idempotent dispatch key), an objective-control outbox redrive (5 000 ms), and a cron-scheduled objective watchdog. A durable workflow and activity ledger sits beside receipts and is best-effort: a durable write failure logs and never fails the already-appended receipt mutation.

### develop/runtime-api — Runtime HTTP and live-event API

### develop/typescript-sdk — The TypeScript SDK and the action contract
purpose: Write a receipt-native agent spec and choose the right side-effect class for each action.
sources: 07
substance: The SDK exports exactly eight values — `receipt`, `defineAgent`, `action`, `assistant`, `tool`, `human`, `merge`, `rebracket` — plus fourteen types. There is no `goal` export: `goal` is a field on the spec. `receipt<T>()` is a pure type marker. A spec is `{id, version, receipts, view(helpers), actions(deps), goal(ctx), mergePolicy?, onMergeResult?, runtimePolicyVersion?, maxIterations?, maxConcurrency?}`, where view helpers provide `on(type).all()/.last()/.exists()` and `chain()`. The action contract: `kind` is action | assistant | tool | human and drives selection priority (human before assistant before action before tool); `execution` is local or remote; `sideEffects` is receipt_only (replay-safe local work), query (local, at-least-once after lease ambiguity, with the buffered output fenced and deduplicated by invocationId through an output manifest) or external (a real mutation, which must be remote and must use invocationId as the downstream idempotency key because remote delivery is at-least-once). Optional members: `when`, `commitWhen` (an optimistic-validity fence re-evaluated inside every retry against both the selected and latest view — returning false records `action.superseded` and reselects), `exclusive` (forces a selection of exactly one), `maxConcurrency` (lowers the per-selection cap, and the effective cap is the minimum across selected actions), `responseWhen` (required for human actions) and `targetGroup` (picks the worker group for a remote action). Determinism: selectionId and invocationId are sha256 digests over the run, spec id and version, policy versions, selected head and action ids, so a recovered run reproduces identical ids; receipt content hashing sorts keys so harmless ordering differences do not invalidate a recovered output manifest. The canonical control receipts are run.started/completed/blocked/failed, action.selected/started/output.manifest/completed/failed/superseded, human.requested/responded, goal.completed, and merge.started/output.manifest/selected/applied/skipped/failed. Remote actions dispatch through a pinned, versioned function whose worker reloads the spec from packages/receipt-app/src/agents/<id>.agent.ts and re-checks provenance, with the refusals 'agent spec '<id>' does not support remote execution', 'remote action '<id>' requires <agent>@<version>, but the worker loaded <agent>@<version>', 'selected head '<hash>' is unavailable', 'no longer matches selected kind/execution provenance' and 'is no longer runnable at its selected head'. A merge policy is `{id, version, shouldRecompute?, candidates, evidence, score, choose}` — shouldRecompute is optional.

### self-hosting/overview — What self-hosted mode actually is
purpose: Prevent every downstream mistake by leading with the build-time constraint and the behaviour differences.
sources: 09, 01, 08, 03d
substance: Self-hosted mode is a build-time choice. VITE_APP_INSTANCE_MODE is resolved once at module load and baked into the browser bundle, so it cannot be changed on a running deployment, and anything other than the exact string `self_hosted` means cloud. None of the repo deploy paths set it to self_hosted — the infrastructure config, the single-host generator and the image build script all pass the literal 'cloud', and the web Dockerfile defaults its build argument to cloud. To get a self-hosted instance you must build the web image yourself with `--build-arg VITE_APP_INSTANCE_MODE=self_hosted` (the Dockerfile accepts and re-exports the argument) and supply SELF_HOSTED_SETUP_TOKEN to the running container; for local use set VITE_APP_INSTANCE_MODE=self_hosted in apps/start/.env.local. Until that is done, four behaviours are unreachable: the /setup claim wizard, the setup token, the invite_only signup policy and the public-app lock. What changes in a self-hosted build: no email OTP plugin and no email verification requirement; social auth blocked with 'Social auth is disabled for self-hosted instances.'; email verification and password recovery blocked with their own message; no anonymous sessions; no Stripe plugin and a static pricing card; email change disabled; /auth/sign-up always redirects and /auth/sign-in redirects to /setup while setup is incomplete; the default plan is self_hosted with 100 000 seats and no signup credit; usage metering is disabled; invitations fall back to copyable signup links when no mail transport is configured; and product telemetry is disabled entirely. The /setup wizard is two steps — 'Hello Human' with a setup token field (the token may also arrive as ?setupToken=, ?setup-token= or ?token= and is stripped from the URL), then 'Create your admin account' — and its refusals are 'The setup token is invalid.', 'The setup token is not configured yet.', 'Self-hosted setup has already been completed.', 'Setup is only available in self-hosted mode.' and 'Failed to finish setup.' It marks the instance claimed with an invite-only signup policy and the public app locked. Signup policies are invite_only (default), shared_secret and open, enforced before signup with 401 'This self-hosted instance has not been claimed yet. Complete setup first.', 403 'A valid shared signup secret is required for this instance.' and 403 'This self-hosted instance currently accepts invite-only signups.' — and there is a real gap: no UI can change the policy or the lock after setup. The readiness checklist the wizard renders covers App URL, Auth secret, Postgres, Redis, Object storage and Setup token as required, with the markdown worker optional. Point readers at apps/start/.env.self-host.example as the only self-host env template, and note that no README or setup document references it.

### self-hosting/configuration — Configuration, secrets, and keys
purpose: Configure a deployment using only variables the code actually reads, and avoid the irreversible key mistake.

substance: Required or the process dies at import: BETTER_AUTH_URL ('Missing BETTER_AUTH_URL. ### self-hosting/database-and-migrations — Postgres, migrations, and the sync publication
purpose: Meet the database requirements and change the schema without silently breaking client sync.
sources: 08, 09, 07
substance: Receipt requires PostgreSQL with logical replication enabled (`wal_level=logical`), because the sync layer replicates from it; the local compose file runs Postgres 16 while CI runs Postgres 17, so pick a version and be explicit. Migrations are timestamped files applied by the migration script with checksum enforcement — add a new file, never edit an applied one — and the destructive commands are the database reset and the sync reset, while the migrate command is safe to run against a live stack. The replication publication is the trap: a table is only replicated to clients when it is a member of the publication, so adding a table means changing the schema and publication membership in one change, and the publication must be refreshed after the Receipt projection tables exist. The correct deploy order is durable-schema pre-migration, then schema migrations, then publication refresh. Symptoms and their causes: a newly published table shows no rows (missing publication membership); the sync cache exits shortly after start following a schema reset (a retained replica file still holds DDL from an earlier schema lifecycle — use a fresh replica file); 'relation "<schema>.receipt_job_projection" does not exist' during migration (ordering). Security detail worth copying: the connection-secret table is published with an explicit column list, so ciphertext, key version and internal ownership metadata are never replicated to a browser even though the status column is. Tenancy: the resolved data directory is hashed into a Postgres schema name (`receipt_data_<24 hex>`) unless an explicit schema is configured, every pool pins its search_path so a role default cannot silently redirect unqualified queries, and the default pool size is 2.

### self-hosting/integrations-provider — Running the integration provider
purpose: Stand up the connector provider so Receipt Connect works at all, including the key bootstrap order.
sources: 10, 09, 08
substance: Receipt Connect requires a self-hosted integration provider; the configuration surface is provider-agnostic but only `nango` is an accepted provider value today. Set RECEIPT_INTEGRATIONS_URL, RECEIPT_INTEGRATIONS_SECRET_KEY and RECEIPT_INTEGRATIONS_WEBHOOK_SECRET or every connect call fails with 'Self-hosted Nango is not configured. Set RECEIPT_INTEGRATIONS_URL, RECEIPT_INTEGRATIONS_SECRET_KEY, and RECEIPT_INTEGRATIONS_WEBHOOK_SECRET.' The bootstrap order is a genuine chicken-and-egg: the secret key is the provider's own prod-environment key, which only exists once the provider's database does — so deploy once, open the integrations UI, copy the prod environment key in its UUID form (not the public key), set it and deploy again. A placeholder that is not a UUID v4 is rejected before upload with an explicit message, and the two base64 encryption keys are validated to decode to exactly 32 bytes. Webhooks are the primary consistency path: set the provider's webhook URL to `<public base>/connect/nango/webhook`, enable HMAC and share the same secret; Receipt verifies an HMAC-SHA256 of the raw body from the `x-nango-hmac-sha256` header with a timing-safe comparison and answers 401 'invalid Nango webhook signature' otherwise. Two webhook shapes are handled: an auth creation or override, which upserts the encrypted reference resolving organization, workspace and connection name from tags (falling back to the Default workspace and the name `default`); and an auth refresh failure, which marks the stored reference invalid. A webhook whose actor has since lost workspace membership is acknowledged with 200, the projection is refused, and the just-created provider connection is best-effort deleted. Read repair is the secondary path: it reconciles the provider's connection list with Receipt's stored references, runs awaited on the connections endpoint and deferred on capabilities (because capabilities sit on the chat preflight path), direct-checks a stored reference the list did not report, and swallows failures so a briefly unreachable provider never deletes stored connections. Operational warnings: the local container ships with a default encryption key and a default dashboard login that must be replaced before it is exposed, and OAuth connectors require you to register a provider app and configure the integration id, while provider-only connectors (API key, PAT, access keys) are auto-created on first use.

### self-hosting/deploying — Deploying Receipt
purpose: Describe the deployment shape, guards and release discipline without any account-specific detail.
sources: 09, 07
substance: Two topologies exist in the repository. A multi-service container deployment runs the web/gateway, the runtime roles, the sync cache, the integration provider and the channel adapters as separate services behind a load balancer with managed Postgres and Redis. A single-host deployment runs the whole stack on one machine with a reverse proxy terminating TLS and the gateway bound to 127.0.0.1:3000. ## GROUP: Factory

### repo/factory-overview — Factory concepts and configuration
purpose: Establish the objective/task/candidate vocabulary and the config file before any command is run.
sources: 06
substance: An objective is a durable receipt-backed goal on `factory/objectives/<id>` with statuses planning, waiting_for_slot, collecting_evidence, evidence_ready, synthesizing, executing, integrating, promoting, completed, blocked, failed and canceled, surfaced as a display state (Draft, Queued, Running, Awaiting Review, Stalled, Blocked, Completed, Archived, Failed, Canceled) and a finer phase detail, with human-readable lines such as 'Queued — Waiting for the repo execution slot.', 'Waiting for computer — Waiting for computer capacity before the agent starts.', 'Collecting evidence — Gathering evidence for the active task.', 'Blocked — Waiting for operator guidance before continuing.' and 'Stalled — Execution stopped making visible progress.' A task is a node in a DAG with dependsOn and statuses pending, ready, running, reviewing, approved, integrated, blocked and superseded, plus an execution phase and an evidence status of empty, partial, sufficient or final; seed the DAG with `--initial-task 'title::prompt'` (repeatable) or `--initial-tasks-json`. A candidate is one sequential attempt at a task. A job is the queued unit behind a task or control action. A check is a shell validation command run against the integration worktree before promotion — and the resolver sends no checks at all for investigation objectives or connected-system objectives. Objective mode is delivery or investigation and severity is an integer 1..5. Only one objective holds the repo execution slot at a time, which is why the board's sections are Needs Attention, Active, Queued, Completed and Archived. Promotion moves through idle, queued, merging, validating, validated, ready_to_promote, promoting, promoted and conflicted, requires ready_to_promote plus an active candidate (else 409 'objective is not ready to promote'), and is refused by a gate with six exact messages about a missing planning receipt, a still-blocked task, no integrated task satisfying the objective, a missing completion contract, missing proof, or remaining work. Auto-promote defaults to true but the runtime forces it false for investigation objectives, and the shipped profile defaults new objectives to investigation — so manual promotion is the practical default. There is exactly one profile, `receipt`, whose action policy allows create, react, promote, cancel, cleanup and archive. Execution: the only execution path is `computer` and the only target is the sandbox provider, with its configuration defaults (domain, image, template version, remote workspace root, 120-second ready and request timeouts, a 3 600-second sandbox timeout, 2 CPU / 4 GiB, a 20-minute idle stop) and two hard guards that refuse a local-only image for remote workers. The task packet lives at `receipt/current/` — objective.json, task.json, manifest.json, context.md, context-pack.json, prompt.md, output/result.json, output/stdout.log, output/stderr.log, output/last-message.md, evidence/evidence.json, skills/skill-bundle.json, memory.cjs, memory-scopes.json and receipt-cli.md — and the checked-in workbench helper exposes `path`, `show` and `finalize`. Prerequisites: ZERO_UPSTREAM_DB, a git repository, a `.receipt/config.json` created by `receipt factory init`, a codex binary, a running runtime to drain the jobs the CLI enqueues, and python3 for the helper catalog. Configuration: the loader reads exactly four policy groups — concurrency.maxActiveTasks (default 5, clamped 1–50), budgets.maxTaskRuns (50, 1–200), budgets.maxCandidatePassesPerTask (4, 1–12), budgets.maxObjectiveMinutes (1440, 1–10080), throttles.maxDispatchesPerReact (10, 1–30) and promotion.autoPromote (true) — plus repoRoot, dataDir, codexBin, repoSlotConcurrency, defaultChecks and schedules; every other key, including several present in the checked-in file, is read and silently discarded, and the parse errors are exact and worth listing.

### repo/authoring-agents — Authoring an agent
purpose: Write and run a receipt-native agent, with the scaffold defect stated up front.
sources: 07, 05
substance: Treat `receipt new <agent-id> [--template basic|assistant-tool|human-loop|merge]` as a template generator, not a working scaffold.
