The released `receipt` CLI is a single compiled binary that ships with the hosted origin `https://app.kentron.ai` baked in, so on the hosted app there is nothing to configure — install it and sign in.

## Install

```bash
curl -fsSL https://raw.githubusercontent.com/kentronai/receipt-cli/main/install.sh | bash
```

The installer drops one executable, `receipt`, into `~/.local/bin`. If that directory is not already on your `PATH`, the script prints the exact line to add — add it to your shell profile to make it stick:

```bash
export PATH="$HOME/.local/bin:$PATH"
```

## Quick start

```bash
receipt --version            # confirm the binary is on your PATH
receipt doctor               # check the CLI can reach the gateway (read-only, no sign-in)
receipt setup                # sign in through your browser and see the connector catalog
receipt workspace current    # show the workspace this session is bound to
receipt mcp install codex    # wire your Receipt tools into the Codex MCP client
```

## What the installer does

- Requires `curl`, `tar`, and a SHA-256 utility (`shasum` or `sha256sum`).
- Downloads the release archive for your platform along with the published `checksums.txt`, verifies the archive against its SHA-256 line, and refuses to install if that does not match.
- Installs one executable — `receipt` — into a local bin directory, `~/.local/bin` by default.
- Re-running it upgrades in place. Your session directory, `~/.receipt`, is left untouched, so an upgrade does not sign you out.

Environment variables the installer reads: `RECEIPT_CLI_VERSION` pins a specific release tag instead of the default the script carries, `RECEIPT_CLI_BIN_DIR` changes the install directory, `RECEIPT_CLI_BIN` sets the exact destination path, and `RECEIPT_CLI_REPO` points at a different release repository. The script reads them from the environment of the shell that runs it, so in a piped install the assignment goes on `bash`, not on `curl`:

```bash
curl -fsSL https://raw.githubusercontent.com/kentronai/receipt-cli/main/install.sh | RECEIPT_CLI_VERSION=<release-tag> bash
```

<Note>
The binary is compiled with dotenv and bunfig autoload disabled, so a stray `.env` or `bunfig.toml` in your working directory cannot change which host the CLI talks to. The endpoint is resolved from the baked-in default and the overrides described below, never from a local file.
</Note>

## Supported platforms

macOS and Linux, on arm64 and x64. Anything else stops with `Unsupported OS` or `Unsupported architecture`.

There is no Windows build, and no npm or Homebrew distribution — the installer script above is the only channel documented here. A package named `receipt` on any package registry is not this CLI.

<Note>
The installer does not install the Claude observer companion binary, even when a release archive bundles one. That is why `receipt setup` can report the observer as not installed on a freshly installed CLI — see [Observing Claude Code](/cli/observe-claude-code).
</Note>

## Verify your install

Before you sign in, run `receipt doctor`. It is read-only — it never opens a browser and never prints a token — so it is the safest way to confirm the CLI is wired up:

```bash
receipt doctor
```

On a fresh hosted install it resolves the endpoint, probes the gateway health and the sign-in URL, and reports that no session is saved yet, ending with `Run 'receipt setup' to sign in.` Add `--json` for a machine-readable envelope. [Check your install with receipt doctor](/cli/doctor) covers the full output and exit codes.

## Dev or self-hosted deployments

Skip this section on the hosted app — the baked-in origin already points at `https://app.kentron.ai`. You only need an override when you run against a self-hosted deployment or a local stack.

Point the CLI at a different gateway either as an environment variable, which every later command in that shell inherits:

```bash
export RECEIPT_CONNECT_PUBLIC_GATEWAY_URL=https://<your-receipt-host>
receipt setup
```

or as a flag on the command itself:

```bash
receipt setup --server-url https://<your-receipt-host>
```

The two are not identical. The environment-variable form produces a `prod` session; `--server-url` produces a `custom` session, which writes no per-target session file. [Signing in](/cli/setup) covers what that difference means for the files on disk. When the web sign-in origin differs from the gateway, set it with `--auth-url`.

For a local stack, use the built-in `local` target instead:

```bash
receipt --target local doctor
receipt setup --target local
```

It defaults to gateway `http://127.0.0.1:8787` and auth `http://127.0.0.1:3000`. Override those with `RECEIPT_CONNECT_LOCAL_SERVER_URL` and `RECEIPT_CONNECT_LOCAL_AUTH_URL`. The auth URL must be the exact origin your browser uses, because the device-approval page needs your Better Auth cookie.
