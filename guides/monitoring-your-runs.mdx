title: "Monitoring your runs"
description: "Every surface Receipt gives you for watching runs, usage, and activity — none of them are in the sidebar."
---

Receipt has several pages built for watching what's running, what it cost, and how the organization is using it. None of them appear in the sidebar. Every one below exists and works — you reach it by typing its URL directly.

## `/tasks` — Beetle Tasks

Tasks are organized into stages: `new`, `queued`, `running`, `blocked`, `reviewing`, `done`, `failed`, and `archived`. The page header shows tiles for **Unresolved**, **Running**, **Blocked**, and **Done**.

A **New Task** button opens a create panel at `/tasks?create=1`, with two lanes to choose from — **Improvement check** and **Add/improve integration** — and fields for Title, Problem, Priority (**P1**–**P4**), Scope, **Context and constraints**, and **Done when**.

Each row carries actions for **Receipts** (opens the same Replay dialog you'd see in chat), **Thread** (jumps to the originating chat thread), **Cancel**, and delete. With nothing tracked yet, the page reads `No Beetle tasks yet`.

## `/sessions` — imported Claude Code activity

This page reads imported Claude Code sessions and surfaces token waste, compliance risk, and replay gaps found in them. Its top metrics are **Sessions**, **Prompts**, **Replies**, **Issues**, and **Evidence**, and it has four modes: **Checks**, **Replay**, **Lessons**, and **Evidence**.

The Checks mode runs a fixed set of named checks against imported sessions: **Token optimization**, **Replay completeness**, **Compliance readiness**, **Lesson candidate**, and **Agent computer review**. Token usage throughout the page is rendered in a compact form, like `12.3k in · 4.5k out · 30k cache`.

With nothing imported yet, the page reads `No imported sessions yet`.

## `/computers` — Beetle runner capacity

This page shows the live state of the compute capacity that runs background objectives: tiles for **Ready**, **Leased**, **Running jobs**, **Waiting jobs**, and **Unhealthy**, plus panels for **Current work**, **Live output**, **Inventory**, and **Active runs**. Selecting a run opens an **Open output** dialog with Status, Task, Trace, Job, Lease, and Computer fields alongside its stdout and stderr.

<Info>
`/computers` is the one surface on this page with an actual link pointing at it: the **Beetle runners** widget in the sidebar footer. Its tooltip reports live counts in the form `<idle> ready, <leased> working, <waiting> waiting, <creating> warming, <unhealthy> unhealthy.`
</Info>

## Usage and Billing

`/organization/settings/usage` and `/organization/settings/billing` have no sidebar entry either. Both require an organization owner or admin role to open, same as the rest of organization settings. The Usage page itself links forward to Billing through its **Upgrade** button — that's the only in-product link between the two.

## Org Brain

At `/organization/settings/knowledge-graph`, Org Brain is a read-only, organization-wide activity dashboard — not a knowledge store and not an editable graph. Like the rest of organization settings, it needs an owner or admin role to open.

You can switch its reporting window between **30**, **60**, and **90** days, and the page refreshes itself automatically every **30 seconds**. Its headline tiles are **Runs**, **Job success**, **In progress**, **Connected apps**, **Avg duration**, and **Total spend**.

<Note>
Wherever Org Brain doesn't have a real measurement for something, it renders `Not recorded` rather than showing a zero — so an untracked value is never mistaken for a genuinely empty one.
</Note>

## The one exception: Replay

The in-chat **Replay** dialog, covered on [Read the receipts](/getting-started/receipts-and-replay), is the only monitoring surface in this whole list that you reach through ordinary navigation rather than a direct URL — it's a button on the chat page itself.

## For self-hosted operators

Receipt's runtime exposes two liveness endpoints, both meant for infrastructure rather than end users:

- `GET /healthz` always returns **200**, and reports whether the service considers itself ready inside the response body.
- `GET /readyz` returns **503** specifically when Postgres doesn't answer, and **200** otherwise.

Receipt does not expose a `/metrics` endpoint of its own.
