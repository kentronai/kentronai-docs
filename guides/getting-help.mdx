The **Docs** link in the sidebar footer — which is how most people find this page — is the only escalation surface Receipt's interface wires up. There's no in-app support widget, ticket form, or live chat behind it. This page is where that link ends.

## Start with troubleshooting

Before looking for a person to ask, check whether the answer is already written down:

- For an error message you saw in chat, search for its exact text on [Errors and limits](/guides/errors-and-limits).
- For a local setup or development failure, work through [Running the repository](/repo/local-development).

## Two dead links to know about

Two places in the product look like they'll connect you to support. Neither one does:

- Organization Settings → Analytics has an **Extraction Analytics** card whose help text reads `Contact support to enable.`, with a **Contact us** link. That link goes nowhere.
- The pricing page's Enterprise and On-Premise plans have **Contact Sales** and **Get in Touch** buttons. Both are dead links too.

If you click either one expecting to reach someone, that's not a bug you're hitting — the destination simply isn't built.

## Not yet available

A few areas of the interface exist but don't do anything yet. If you find one of these, you haven't misconfigured something — none of them are active in this release:

- **Model Gateway → Playground** is not active in this release.
- **Agents → Dashboard** and **Agents → Registry** are not active in this release.
- **Single sign-on** — including domain verification and directory provisioning, under Organization Settings → Security — is not active in this release.
- **Extraction analytics**, under Organization Settings → Analytics, is not active in this release.
- **Guardrail enforcement** is not active in this release.

## Reporting a security issue

Security reports shouldn't go through public GitHub issues. Wherever you're asked to report one, include:

- The issue type (for example, buffer overflow, SQL injection, or XSS)
- The full source paths involved
- A tag, branch, commit, or direct URL that pins the version you're reporting against
- Any special configuration needed to reproduce it
- Step-by-step reproduction instructions
- Proof-of-concept or exploit code, if you have it
- The impact, including how an attacker might exploit it

## For self-hosted operators

If you run your own Receipt deployment, these machine-readable endpoints are the fastest way to check whether a service is actually up, ahead of anything in the interface:

- `GET /healthz` on the runtime always returns **200**, and reports whether the service considers itself ready inside the response body.
- `GET /readyz` on the runtime returns **503** specifically when Postgres doesn't answer, and **200** otherwise.
- `GET /health` on the web app returns `{"ok":true}`.

<Warning>
Receipt doesn't ship a support address. Who to contact, and how, is something your Receipt operator configures — ask them, rather than treating the dead links above as evidence that one exists.
</Warning>
